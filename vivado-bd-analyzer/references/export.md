# Export reference

## bd_graph.json schema

```json
{
  "meta":  {"schema": 1, "design": "pkt_proc", "bd_file": "/abs/path/pkt_proc.bd", "vivado": "2023.2", "exported": "2026-10-14T10:00:00"},
  "cells": [{
    "path": "/pe_0/fifo",
    "kind": "xilinx_ip | module_ref | hls | custom_ip | hier",
    "vlnv": "xilinx.com:ip:axis_data_fifo:2.0",
    "ref":  "hdr_switch",
    "config": {"FIFO_DEPTH": ["1024", "USER"]},
    "intf_pins": [{"name": "S_AXIS", "mode": "Slave", "vlnv": "xilinx.com:interface:axis_rtl:1.0"}],
    "pins": [{"name": "s_axis_aclk", "dir": "I", "type": "clk", "left": "", "right": ""}]
  }],
  "ports": [{"path": "/M_AXIS_QDMA", "intf": true, "mode": "Master", "vlnv": "..."},
            {"path": "/gate_stat", "intf": false, "dir": "O", "type": "data", "left": "31", "right": "0"}],
  "intf_nets": [{"path": "/pe_0/S_AXIS_1", "vlnv": "...", "src": ["/pe_0/S_AXIS"], "dst": ["/pe_0/fifo/S_AXIS"]}],
  "nets":      [{"path": "/axis_aresetn_1", "type": "clk | rst | intr | data", "src": ["..."], "dst": ["..."]}],
  "addr":      [{"seg": "/ingress_parser/s_axi_control/Reg", "offset": "0xA0000000", "range": "64K"}]
}
```

`meta.schema` is bumped by `bd_export.tcl` when the layout changes incompatibly; bdq warns when a
graph is newer than it understands (graphs without it are schema 0, the same layout as 1).

String values are JSON-escaped, including every control character (`\u0001` …).

`src`/`dst` are already resolved from the point of view of each net: a hierarchy boundary pin is a
sink on the outer net and a driver on the inner net, and top-level input ports are drivers. bdq
merges nets joined through hierarchy pins, so paths and peers cross hierarchies transparently.

## Vivado properties relied on

| Object | Properties | Used for |
|---|---|---|
| cell | `PATH`, `VLNV`, `TYPE`, `REFERENCE_NAME`, `CONFIG.*`, `CONFIG.*.VALUE_SRC` | kind, source lookup, non-default config |
| intf pin / port | `CLASS`, `MODE`, `VLNV`, `NAME` | direction, interface type |
| pin / port | `CLASS`, `DIR`, `TYPE`, `LEFT`, `RIGHT` | direction, clk/rst/intr detection, width |
| addr seg | `OFFSET`, `RANGE` | address map |
| design | `NAME`, `FILE_NAME` | metadata, staleness check |

Every property read is wrapped in `catch`, so a missing property yields an empty string instead of
an error. Symptoms and checks:

- **All config shown, no "user-set only"**: `CONFIG.X.VALUE_SRC` is not available in this version.
  Check with `get_property CONFIG.<KEY>.VALUE_SRC [get_bd_cells <cell>]`.
- **Connections with empty src or dst**: check `get_property CLASS`, `MODE`, `DIR` on the pins of
  that net: `foreach p [get_bd_intf_pins -of [get_bd_intf_nets <net>]] {puts "$p [get_property MODE $p]"}`.
- **kind is custom_ip for an RTL block**: check `get_property VLNV` and `TYPE` of the cell. Module
  references normally have `TYPE module_ref` or a VLNV with library `module_ref`.
- **Clock/reset nets classified as data**: the pins lack `TYPE clk|rst` (common for module_ref pins
  without X_INTERFACE attributes). Adding `(* X_INTERFACE_INFO = "xilinx.com:signal:clock:1.0 aclk CLK" *)`
  in the RTL fixes it in Vivado too.
- **Slow export**: HBM, DDR4, PCIe and QDMA IPs have thousands of CONFIG keys. Pass a skip glob as the
  4th batch argument (or 2nd argument of `bdx_export`), e.g. `"*hbm*"`.

## Source lookup rules (bdq src)

1. `src_map` in `bdq.json` (keys: full path, short path or leaf name) wins.
2. `module_ref` / `custom_ip`: files under `src_roots` declaring `module <ref>` or `entity <ref> is`.
   `<ref>` is `REFERENCE_NAME`, otherwise the VLNV name field.
3. `hls`: C/C++ files defining the top function (VLNV name), plus HLS configs
   (`syn.top=`, `set_top`, `topfunction name=`).
4. Files under `*.runs`, `*.cache`, `*.gen`, `*.sim`, `*.ip_user_files`, `.Xil` are skipped; files in
   HLS output folders or with a "Generated by Vitis HLS" header are marked GENERATED.

For packaged custom IP whose top module name differs from the VLNV name, add a `src_map` entry.

What each file declares (modules, entities, C++ function definitions, HLS tops, generated flag) is
cached in `<workdir>/.cache/src_index.json`, keyed by path and refreshed when size or mtime changes.
Deleting it is always safe. It is only written when there is a work directory and the write is
allowed; otherwise lookups simply scan the files.

## How `bdq export` keeps the project untouched

`bdq export` builds one shell script and runs it with the local Vivado (`bash -c`), aborting after `--timeout` seconds (default 3600, or
`vivado.timeout`). The script:

1. create a temp directory with `mktemp -d` and remove it on exit (`trap ... EXIT`);
2. write `bd_export.tcl` into it from **stdin** (the script is never copied into the project);
3. `cd` into the temp directory, so Vivado's own litter (`.Xil/`, `vivado_pid*.str`) lands there;
4. source `settings64.sh` (its output is discarded), run Vivado in batch mode with the project
   opened via `open_project -read_only`, sending Vivado's log to stderr;
5. `cat` the graph to stdout.

bdq parses stdout and writes the graph into the **work directory** (atomically, via a `.tmp`
file). Any path outside the work directory is refused, including `--out` values and `bdq.json`.
If the installed Vivado cannot open the project read-only, the exporter stops with an error
instead of falling back to a writable open.

Vivado may still update per-user state in the home directory of the account running it
(e.g. `~/.Xilinx`); that is outside the project.

## Hard guarantees (recommended)

The write policy in SKILL.md and the checks in bdq are strong, but an operating-system guarantee
is better: expose the project through a read-only bind mount, or run with a user that lacks
write permission on it. Nothing can then modify the project, while the work directory (a folder
outside it) stays writable.
Claude Code permission rules (deny rules for edits under the project path) add another layer;
check the current syntax in the Claude Code permissions documentation.
